# Задание вопросов пользователю

## Главный принцип

Когда агенту нужно уточнение от пользователя, он **ОБЯЗАН** использовать встроенные механизмы среды выполнения. Агент **НЕ ИМЕЕТ ПРАВА** продолжать работу с допущениями, пока есть нерешённые вопросы.

## Механизм для Cursor IDE

В Cursor используется инструмент **`AskQuestion`** — он предъявляет пользователю структурированные вопросы с множественным выбором.

### Формат вызова AskQuestion

Каждый вопрос содержит:
- `id` — уникальный идентификатор вопроса
- `prompt` — чёткая формулировка вопроса
- `options` — массив вариантов ответа (минимум 2):
  - Каждый вариант имеет `id` и `label`
  - **Последний вариант ВСЕГДА** — «Другое (опишите)» / "Other (describe)"
- `allow_multiple: true` — когда допустим множественный выбор

### Пример вызова

```json
{
  "questions": [
    {
      "id": "api-contract",
      "prompt": "record.set() должен принимать (field, value) или весь объект состояния?",
      "options": [
        { "id": "field-value", "label": "record.set(fieldName, value) — запись одного поля" },
        { "id": "object", "label": "record.set(state) — замена всего объекта" },
        { "id": "other", "label": "Другое (опишите)" }
      ]
    }
  ]
}
```

## Язык вопросов

**Обязательное правило:** все вопросы пользователю формулируются на языке `USER_LANGUAGE`:
- Читай `USER_LANGUAGE` из `requirements_lock.md` (предпочтительно)
- Если `requirements_lock.md` недоступен — из `segment_analyst_output.md`
- Если язык не определён — используй язык оригинального ТЗ

## Требования к формулировке вопросов

1. **Конкретность:** вопросы должны быть конкретными и actionable — не расплывчатые «это ОК?»
2. **Варианты:** каждый вариант ответа описывает конкретный сценарий, не абстрактный
3. **Escape hatch:** всегда включать вариант «Другое (опишите)» как последний вариант — пользователь может описать свой ответ свободным текстом, если ни один из предложенных вариантов не подходит
4. **Квиз-формат:** вопросы ОБЯЗАТЕЛЬНО структурированы как квиз (не свободная форма), чтобы вынудить точность от пользователя

## Градационная линия

Вопросы задаются **раундами**. Каждый раунд углубляется в контекст:

1. **Раунд 1:** верхнеуровневые вопросы — общая стратегия, выбор подхода
2. **Раунд 2:** детализация — конкретные контракты, поведение edge cases
3. **Раунд 3:** финальные уточнения — остаточные неясности

Повторяй раунды пока задача не перестанет требовать уточнений или пользователь явно не скажет «продолжай как есть».

## Запрет на допущения

- Агент **НЕ ИМЕЕТ ПРАВА** принимать решения за пользователя при наличии неясности
- Если ответ пользователя не снимает неясность — задай уточняющий вопрос в следующем раунде
- Если пользователь выбрал «Другое» — проанализируй свободный ответ и при необходимости задай уточняющий вопрос

## Кто может задавать вопросы

| Фабрика | Агент | Когда |
|---------|-------|-------|
| analytics-factory | `analyst` | При обнаружении неясностей в задаче |
| analytics-factory | `final_analyst` (через analyst) | При обнаружении неясностей при декомпозиции |
| code-factory | `task_analyst` | При трансляции вопросов от architect |
| code-factory | `architect` (через task_analyst) | При обнаружении неясностей при проектировании |

Инженеры и разработчики **НЕ задают вопросов через квиз** — они создают блокеры.
